## Incident #20 — F18: `main.sqlite` (memory-core builtin) corrompido

### Sintoma

`openclaw doctor --fix` reportava `Memory artifact repair could not be completed: database disk image is malformed`. `openclaw memory status` falhava completamente com stack trace apontando pra `MemoryIndexManager.status()` em `manager-I95n2oMo.js:3037`.

### Investigação

1. **Confirmar que NÃO é false positive:** `openclaw memory status` rodado standalone reproduziu o erro real (não só ruído do doctor).
2. **Identificar DB:** `strace -f -e openat openclaw memory status` capturou:
   ```
   openat(AT_FDCWD, "/root/.openclaw/memory/main.sqlite", O_RDWR|O_CREAT|O_NOFOLLOW|O_CLOEXEC, 0644) = 21
   ```
   logo antes do crash.
3. **Confirmar corrupção:** `sqlite3 /root/.openclaw/memory/main.sqlite 'PRAGMA integrity_check;'` retornou:
   ```
   *** in database main ***
   Tree 2516 page 30067: btreeInitPage() returns error code 11
   Tree 2516 page 33186: btreeInitPage() returns error code 11
   Tree 2516 page 30472: btreeInitPage() returns error code 11
   Tree 2517 page 29163: btreeInitPage() returns error code 11
   ```
4. **Discriminar do `nox-mem.db` próprio do Toto:**
   - `/root/.openclaw/workspace/tools/nox-mem/nox-mem.db` (1.18 GB) → integrity **ok**, 70.029 chunks
   - `/root/.openclaw/memory/main.sqlite` (132 MB) → **corrompido**
   - Outros 6 agent .sqlite (atlas/boris/cipher/forge/layca/nox) → todos **ok**
5. **Last write:** 2026-05-01 09:54 BRT. Bate com janela do upgrade 5.1 → 5.2 (release `v2026.5.2` em 2026-05-02). Provável corrupção durante schema/format change do `memory-core` plugin builtin.

### Root cause hipótese

Schema/format mismatch durante upgrade 5.1 → 5.2 do plugin `@openclaw/memory-core` corrompeu B-tree pages do `main.sqlite` durante write final. WAL ausente confirma DB foi fechado, mas com state inconsistente.

### Fix

```bash
mv /root/.openclaw/memory/main.sqlite /root/.openclaw/memory/main.sqlite.bak-corrupt-20260509-2031
# OpenClaw recria DB vazio na próxima invocação
openclaw memory status  # → Indexed: 0/320 files · 0 chunks · Dirty: yes ✅
```

Custo: zero. Stack do Toto usa `nox-mem` (sistema próprio), não `memory-core` builtin. Index vai re-popular do `MEMORY.md` + sources sob demanda.

### Lesson learned

**Sempre validar QUAL DB está malformed via strace antes de aplicar repair.** A confusão entre `memory-core` builtin (`/root/.openclaw/memory/main.sqlite`) e `nox-mem.db` próprio do Toto (`/root/.openclaw/workspace/tools/nox-mem/nox-mem.db`) é fácil — ambos são "memory" SQLite. O agent paralelo do Toto sugeriu `nox-mem reindex` (que reindexaria o DB SAUDÁVEL e não tocaria o corrompido). Sem strace + integrity_check granular, perderia tempo.

## Incident #21 — F17: Gateway memory growth (forensics parciais)

### Padrão histórico (7 dias, 2026-05-02 → 2026-05-09)

Peak escala com **CPU consumed**, não pure time-decay:

| Cycle | CPU | Memory peak |
|---|---|---|
| Outlier 2026-05-09 | 58min | 8.6 GB + 389M swap |
| Heavy workload | 6h56min | 4.9 GB |
| Várias 3h | 26-50min | 2.3-4.1 GB |
| Restart loops | <2min | 0.6-1.8 GB |

Sugere leak **proporcional ao trabalho**, não pure time-decay — compatível com handler accumulation, prepared-statement leak em SQLite native, ou Map/Set crescendo sem eviction.

### Forensics state-snapshot

- VmPeak: 22.4 GB (virtual address space — Node.js V8 reserva muito, sem significado real)
- VmHWM: 1.19 GB (peak resident)
- VmRSS: 630 MB (current)
- RssAnon: 580 MB (heap-like + native arenas)
- 10 threads (Node.js libuv worker pool)
- **Único `.node` native binding carregado:** `@photostructure/sqlite.glibc.node` (do graph-memory plugin)

### Hipóteses ranqueadas

| # | Suspeito | Evidência |
|---|---|---|
| 1 | **graph-memory plugin v1.5.8** (third-party) | Único `.node` binding visível; embedding dim 3072 (alto); source TS custom 34 KB |
| 2 | WhatsApp Baileys session state | Mantém presença/contacts em RAM, cresce com volume |
| 3 | Channel listeners (Discord/Slack/Telegram) | Event handlers + draft state acumulando |
| ❌ | Reranker/ONNX | NÃO carregado no gateway — só no nox-mem-api (esse é I12 separado) |
| ❌ | Stale bash 552107 (4 dias) | RSS 2 MB, killed mas era irrelevante |
| ❌ | delivery-queue | 64 KB, 1 file |

### Mitigação aplicada (defesa-em-profundidade)

```bash
systemctl set-property openclaw-gateway.service MemoryHigh=3G MemoryMax=4G
```

- `MemoryHigh=3 GB` — kernel pressure quando aproxima
- `MemoryMax=4 GB` — OOM hard cap (circuit breaker antes do RAM da VPS estourar)
- Persistente em `/etc/systemd/system.control/openclaw-gateway.service.d/50-Memory{High,Max}.conf`
- Live aplicado sem restart

Cron preventivo de 3h continua ativo como segunda camada. MemoryMax garante que se algum ciclo passar de 4 GB, OOM kill antecipa o cron (em vez de esperar até 22:27 com risco de 8+ GB).

### Watcher live deployado

Script `/root/gw-memory-watch.sh` polling 10min, emite eventos no `/var/log/gw-monitor.log`:
- `START` — baseline inicial
- `TICK` — checkpoint horário (sinal de vida + valor)
- `THRESHOLD` — RSS cruzou 2/4/6/8 GB (uma vez por threshold)
- `RESTART` — pid mudou
- `DOWN` — gateway sumiu

Filtro seletivo (não emite cada poll, só eventos significativos).

### Próximo passo (próxima sessão — experimento B)

Disable graph-memory por 1 ciclo de 3h e comparar peak. Se peak < 2 GB → confirma graph-memory como culprit. Se peak > 3 GB → avançar pra experimento C (re-enable graph-memory + disable WhatsApp).

⚠️ Risco do experimento B: personas perdem recall semântico durante a janela. Aceitável só pra teste de 3h, NÃO produzir output crítico nesse intervalo.

### Lesson learned

**Cron preventivo (3h restart) mascara leak própria do Gateway, não só do nox-mem-api.** Histórico de peaks só ficou visível com `journalctl | grep "memory peak"`. Sem `MemoryHigh/Max` no systemd, defesa única era o cron — fragil.

`set-property` com cgroup limits é defense-in-depth: se cron falhar (host frio, lock contention, drift), kernel limita antes de OOM-killer global atacar serviços não relacionados (nox-mem-api, tailscale).

## Incident #22 — `plugin-runtime-deps` ENOTDIR salvou o emoji patch

Doctor reportou `Legacy plugin-runtime-deps: erro ENOTDIR ao tentar remover`. Investigação revelou que o dir `/root/.openclaw/plugin-runtime-deps/openclaw-2026.4.29-4eca5026e977/` contém o **emoji patch session-status** (Regra 2.1 do CLAUDE.md): `dist/status-message-Bwz2ekKl.js` com `chattr +i` ativo, 2 ocorrências de `OAuth (Max)`.

**ENOTDIR foi sorte que protegeu o patch.** Se o doctor tivesse conseguido remover (algum file não-dir tropeçou), destruiria o patch.

### Lesson learned

Doctor `--fix` não tem awareness de patches custom. **Nunca rodar `--fix` em modo destrutivo automatizado.** Sempre revisar lista de actions antes de confirmar. ENOTDIR é random — não confiar como salvaguarda.
