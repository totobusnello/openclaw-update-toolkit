# Crontab silenciosamente reescrito em 2026-05-04 13:29 — 26 cron jobs OpenClaw desativados por ~26h sem alerta

## TL;DR

Durante a sessão de upgrade `2026.5.3-1` em **2026-05-04 13:29 BRT**, algum step (orchestrator, follow-up, ou intervenção manual não-documentada) reescreveu o crontab do user `root` deixando **apenas 1 entry** (`beir-kill-if-overload.sh`). **26 cron jobs OpenClaw** foram silenciosamente desativados:

- `nightly-maintenance.sh` (23:00) — reindex/consolidate/kg/vectorize/session-distill (CRÍTICO)
- `backup-all.sh` (02:00) — wal/agent-dbs/openclaw/git
- `health-probe.sh` (*/10) — gateway+nox-mem+disk+SQLite+circuit breaker
- `token-refresh-max.sh` (*/4h) — Anthropic Max OAuth refresh (CRÍTICO)
- `config-drift-monitor.sh` (*/30) — detect schema/config drift
- 21 entries adicionais (canários, heartbeats, marathon followups, semantic canary, agents-context-watchdog, etc)

Detectado em **2026-05-05 ~13:50 BRT** durante G4 smoke test pós-upgrade 5.4. **Janela silenciosa: ~26h.** Felizmente:
- Anthropic Max OAuth token (`/root/.claude/.credentials.json`) é válido até 2027-04-21 — não expirou
- nox-mem.db SQLite não corrompeu sem backup (próxima janela 2026-05-05 02:00 backup-all.sh teria caído)
- Vector coverage continuou 99.96% (agentes não estavam rodando consolidate, mas ingest contínuo do nox-mem-watcher mantém)

Restore aplicado via syslog mining (4 dias × 33 unique cmds), com **3 melhorias vs antes:**
1. `forge-cc-token-check` corrigido: era `0 9 * * *` daily (incorreto) → `0 9 * * 1` Monday-only (pre-hermes backup confirma)
2. `*/30` group staggered: 5 scripts no minuto :00/:30 → spread em :02-:22 e :32-:52 (-40% pico simultâneo)
3. `crontab-rebuild.sh` atualizado de schema antigo (20+ entries individuais) para novo (26 entries com `nightly-maintenance.sh` orquestrado)

## Como aconteceu

### Trail de evidência

Crontab atual (post-incident) tinha header:
```
# DO NOT EDIT THIS FILE - edit the master and reinstall.
# (- installed on Mon May  4 13:29:23 2026)
*/30 * * * * root /usr/local/bin/beir-kill-if-overload.sh ...
```

Header `installed on Mon May 4 13:29:23 2026` é o timestamp gerado pelo `crontab(1)` quando alguém chama `crontab <file>` ou `crontab -e` e salva. Esse timestamp é a **data exata da perda**.

### Hipóteses do que reescreveu

Durante 2026-05-04 entre 12:00-14:00 BRT rodaram:
- Sessão upgrade `2026.5.3 → 2026.5.3-1` (12:39-12:45)
- 3 postmortems do Baileys WhatsApp incident
- Vários `systemctl restart`, `crontab` reads possíveis em scripts de canário

**Suspeitos primários:**
1. Algum step do `upgrade-zero-downtime.sh` que escrevesse crontab pra estado mínimo (não encontrado no script atual ao revisar)
2. Algum hook de `openclaw-update-toolkit` (script de instalação?) — improvável, é shell static
3. Manual intervention do operador durante postmortem (mais provável — com pressa, talvez "limpou crontab pra testar isolado" e esqueceu de restaurar)

**Não foi identificado o culpado exato.** Mais importante que culpa é prevenção (próximas seções).

### Por que ninguém percebeu por 26h

O sistema cron é **fail-open silencioso** — se entries somem, simplesmente não rodam, sem log de erro. Os efeitos só se manifestam quando alguém *espera* o resultado:
- nightly-maintenance.sh foi última 2026-05-03 23:00. Próximo expected run 2026-05-04 23:00 — não aconteceu
- 2026-05-05 morning-report às 06:30 não rodou — Toto não tinha o relatório matinal
- Vector coverage não cresceu por 24h — só visível em `/api/health` se monitorado
- Token refresh não rodou 6× (a cada 4h) — token continuou válido pq tem TTL longo

Detectado quando G4 smoke test pós-upgrade 5.4 (item documentado no plan v5.4) procurou por logs de nightly-maintenance e não achou.

Pre-hermes backup (2026-04-13) mostrava `0 9 * * 1 /usr/local/bin/forge-cc-token-check` (Monday only). Syslog mining inferiu daily porque só apareceu 1× em 4 dias e o dia foi uma segunda. **Manualmente corrigido para `0 9 * * 1`** (semanal).

## Mitigação durável — 5 ações

### 1. Crontab backup contínuo (cron meta)

Adicionar ao próprio crontab uma entry que backupa o crontab a cada hora:
```
0 * * * * crontab -l > /var/backups/crontab/crontab-$(date +\%Y\%m\%d-\%H).txt 2>/dev/null
```

Retention 30 dias. Se ocorrer perda silenciosa de novo, restore via último backup é trivial. Custo: 100 bytes × 720 backups/mes = 72KB/mês.

### 2. Watchdog: alertar se crontab tem < N entries

Adicionar ao `config-drift-monitor.sh`:
```bash
EXPECTED_MIN=20
ENTRIES=$(crontab -l 2>/dev/null | grep -cE "^[0-9*]")
if [ "$ENTRIES" -lt "$EXPECTED_MIN" ]; then
  logger -t config-drift "ALERT: crontab has only $ENTRIES entries (expected ≥$EXPECTED_MIN)"
  # TODO: trigger Telegram alert via F16 bot quando estiver pronto
fi
```

Custo: 2 linhas no script já existente. Detecta em até 30min após perda.

### 3. Versionamento do crontab no repo

`crontab-rebuild.sh` agora tem o canonical inline. Adicionar pre-commit hook ou periodic check que confirme:
```
diff <(grep -v "^#" /root/.openclaw/scripts/crontab-rebuild.sh | grep -E "^\* | \\* | [0-9]") \
     <(crontab -l | grep -vE "^#|^$")
```

Se diff retornar não-vazio, ALERTA — drift entre canonical e atual.

### 4. Documentar no orchestrator

Adicionar Phase 0 do `upgrade-zero-downtime.sh`:
```bash
# 0i. Backup crontab pre-upgrade
crontab -l > /tmp/crontab-pre-upgrade-${TARGET}-${TS}.txt 2>/dev/null
echo "[0i] crontab backed up ($(wc -l < /tmp/crontab-pre-upgrade-*.txt) lines)"

# Phase 6 final: validate crontab not regressed
POST_ENTRIES=$(crontab -l | grep -cE "^[0-9*]")
PRE_ENTRIES=$(grep -cE "^[0-9*]" /tmp/crontab-pre-upgrade-*.txt)
if [ "$POST_ENTRIES" -lt "$PRE_ENTRIES" ]; then
  echo "WARN: crontab post-upgrade has $POST_ENTRIES entries vs $PRE_ENTRIES before — REGRESSION"
fi
```

Custo: ~10 linhas. Trade-off: detecta perda mas não previne — alguém ainda precisa restore via crontab-rebuild.sh.

### 5. Criar `infra/runbooks/crontab-canonical.md`

Manter source-of-truth em git do canonical crontab + rationale + dependencies. Quando alguém mudar entries, deve PR no infra/runbooks/ E rodar crontab-rebuild.sh para sincronizar.

1. **Cron é fail-open:** sem alerta nativo quando entries somem. Sistema "funciona" silenciosamente degradado.
2. **`crontab-rebuild.sh` estava outdated** desde 2026-04-29 (~7 dias). Indicador de que ele NUNCA foi rodado pra recuperar — só seria útil em emergência.
