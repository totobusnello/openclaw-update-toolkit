## 2. Schema breaking changes em 5.3+

Descobertos durante dry-runs do upgrade 5.3-1. Nosso orchestrator gerava staging config com schema 5.2 que 5.3+ rejeita:

### 2a. `gateway.mode` agora obrigatório

```
Gateway start blocked: existing config is missing gateway.mode.
Treat this as suspicious or clobbered config.
Re-run `openclaw onboard --mode local` or set gateway.mode=local manually,
or pass --allow-unconfigured.
```

**Antes (5.2):**
```json
"gateway": { "port": 18789, "reload": { "mode": "off" } }
```

**Agora (5.3+):**
```json
"gateway": { "mode": "local", "port": 18789, "reload": { "mode": "off" } }
```

Valores válidos pra `gateway.mode`: `local` (canonical pra deployments isolados) ou outros que não tinham documentação clara no momento.

### 2b. `agents.<id>` no top level rejeitado

```
Gateway failed to start: Invalid config at /tmp/openclaw-staging-workspace/openclaw.json.
agents: Unrecognized key: "staging-test"
Run "openclaw doctor --fix" to repair, then retry.
```

**Antes (5.2):**
```json
"agents": {
  "staging-test": { "persona": "...", "model": {...} },
  "defaults": { "model": {...} }
}
```

**Agora (5.3+):** apenas `agents.defaults` e `agents.list[]` são válidos no top level. Custom agent IDs precisam estar dentro de `list[]`:
```json
"agents": {
  "list": [
    { "id": "staging-test", "persona": "...", "model": {...} }
  ],
  "defaults": { "model": {...} }
}
```

Para staging do orchestrator, simplificamos removendo o agent custom — apenas `agents.defaults` é suficiente pra smoke tests:
```json
"agents": {
  "defaults": {
    "model": { "primary": "anthropic/claude-sonnet-4-6", "fallbacks": [...] },
    "compaction": { "keepRecentTokens": 8000 }
  }
}
```

### Onde isso já está documentado

- `infra/CLAUDE.md` regra #1 já cita: *"Per-agent override fica em `agents.list[]`, não `agents.<id>` (object não existe)."*
- O orchestrator agora gera config compliant com 5.3+ schema (commit `6a8f377` em openclaw-vps, commit `9f7a3e0` em toolkit público)

## 3. Slack channel 5.3+ — Socket Mode requer 3 tokens

Plugin `@openclaw/slack` 5.3 default mode = `"socket"`. Bolt SDK em Socket Mode usa **3 tokens distintos**:

| Token | Onde gerar |
|---|---|
| Bot OAuth (BOT_TOKEN) | Slack app config → OAuth & Permissions → Bot User OAuth Token |
| User OAuth (USER_TOKEN) | Slack app config → OAuth & Permissions → User OAuth Token |
| **App-Level Token (APP_TOKEN)** | Slack app config → **Basic Information → App-Level Tokens → Generate Token and Scopes** (scope `connections:write`) |

Plugin `hasSlackConfiguredState()` em `/usr/lib/node_modules/openclaw/dist/extensions/slack/configured-state.js`:

```javascript
const SLACK_CONFIGURED_ENV_KEYS = [
  "SLACK_APP_TOKEN",
  "SLACK_BOT_TOKEN",
  "SLACK_USER_TOKEN"
];
function hasSlackConfiguredState(params) {
  return SLACK_CONFIGURED_ENV_KEYS.some(
    (key) => typeof params.env?.[key] === "string" && params.env[key]?.trim().length > 0
  );
}
```

Var nomes literais — `SLACK_TOKEN` (sem `_USER_`) **não é lido** pelo plugin. Tem que ser exatamente `SLACK_USER_TOKEN`, `SLACK_BOT_TOKEN`, `SLACK_APP_TOKEN`.

Nosso `.env` tinha `SLACK_TOKEN` (legado) + `SLACK_BOT_TOKEN` mas faltava `SLACK_USER_TOKEN` e `SLACK_APP_TOKEN`. Fix:

```bash
# add proper var names
echo "SLACK_USER_TOKEN=<your-user-oauth-token>" >> /root/.openclaw/.env
echo "SLACK_APP_TOKEN=<your-app-level-token>" >> /root/.openclaw/.env

# enroll channel via CLI
openclaw channels add --channel slack --account default --use-env

# restart gateway
systemctl restart openclaw-gateway
```

Pós-restart, channel reporta:
```
- Slack default: enabled, configured, running, connected, bot:env, app:env, health:healthy
```

### Como obter SLACK_APP_TOKEN

1. https://api.slack.com/apps → seu app
2. Sidebar → **Basic Information**
3. Scroll até **App-Level Tokens** → **Generate Token and Scopes**
4. Nome: qualquer (ex: `prod`)
5. Add Scope: `connections:write`
6. Copy token (aparece UMA VEZ — guardar)
7. Add ao `.env` como `SLACK_APP_TOKEN=<token-aqui>`

### Alternativa: HTTP Mode

Se não quiser App Token, pode setar channel para HTTP/Events mode (requer URL pública + webhook handshake). Mais fricção. Socket Mode é o caminho recomendado pra deployment privado.

## 4. GEMINI_MAIN_API_KEY rotation procedure

`.env` tinha 3 chaves Gemini:
- `GEMINI_API_KEY` — funcional (mesma key compartilhada com `GEMINI_WEB_API_KEY`)
- `GEMINI_WEB_API_KEY` — funcional (= mesmo valor de `GEMINI_API_KEY`)
- `GEMINI_MAIN_API_KEY` — **expirada upstream** (key value diferente, ainda no `.env`)

A `MAIN` foi confirmada inválida testando contra Google API direto:

```bash
curl -s -X POST "https://generativelanguage.googleapis.com/v1beta/models/gemini-embedding-001:embedContent?key=$GEMINI_MAIN_API_KEY" ...
# →
{
  "error": {
    "code": 400,
    "message": "API key expired. Please renew the API key.",
    "reason": "API_KEY_INVALID"
  }
}
```

5 backups de `.env` desde 2026-05-01 mostraram que o **valor** de `GEMINI_MAIN_API_KEY` no `.env` nunca mudou — significa **Google invalidou no console sem nosso conhecimento** (key foi deletada/desabilitada manualmente, ou auto-rotation policy do projeto).

### Fix aplicado

Toto forneceu key working (mesmo valor da `GEMINI_API_KEY` atual). Atualizamos a `MAIN` para apontar pro mesmo valor:

```bash
cp /root/.openclaw/.env /root/.openclaw/.env.bak-pre-gemini-fix-$(date +%Y%m%d-%H%M%S)
sed -i 's|^GEMINI_MAIN_API_KEY=.*|GEMINI_MAIN_API_KEY=<new-working-key>|' /root/.openclaw/.env
# verify all 3 keys return HTTP 200
```

Pós-fix, todas 3 vars apontam pro mesmo working key. Operacionalmente nada usava `MAIN` (nox-mem e graph-memory usam `GEMINI_API_KEY` direto), mas higiene importa.

### Procedure pra próxima rotation

1. Detectar key expirada via probe live: `curl ... | jq -r '.error.message'`
2. Comparar value em `.env` com Google AI Studio console (https://aistudio.google.com/app/apikey)
3. Se valor difere → atualizar `.env`
4. Se valor bate mas Google diz expired → key foi invalidada upstream, gerar nova no console + atualizar `.env`
5. Backup: `cp .env .env.bak-pre-rotation-$(date +%Y%m%d)`
6. Restart serviços que usam essa key (nox-mem-api, openclaw-gateway)

## 5. Lições generalizáveis

1. **Defense-in-depth empírico vence retórico.** Layers redundantes só convencem depois de testados — o real upgrade 5.3 → 5.3-1 foi a prova.
2. **Hotfixes são oportunidades baratas de validar fixes.** Patch increment (5.3 → 5.3-1) tem zero breaking; perfeito pra rodar orchestrator novo sob risco controlado.
3. **Schema breaks em patch versions sem aviso explícito.** Nem release notes mencionavam `gateway.mode` agora obrigatório nem `agents.list[]` rejection. Testar sempre o schema do staging config contra binary novo, não confiar em release notes.
4. **Channel onboarding tem layers**: env vars, `openclaw.json` config, `openclaw channels add`, plugin manifest. Falha em qualquer um → "not configured". Documentar todos.
5. **Vendor key rotation não é evento previsível.** Google AI Studio pode invalidar keys sem notificação. Health checks devem incluir live key probe (HTTP 200 vs 4xx) periodicamente.
6. **Smoke tests do orchestrator devem evoluir com schema upstream.** Cada major/minor da plataforma pode quebrar staging config — o orchestrator precisa ser self-healing nessa frente.
