## Incidente 7 (P1) — Nox respondendo em grupo WhatsApp sem mention

### Sintoma
Toto observou Nox respondendo a mensagens em grupo WhatsApp `<REDACTED-WHATSAPP-GROUP>` sem ser explicitamente mencionado. Cada inbound 08:13/14/19/22/25 disparou `cli exec` 2-3s depois.

### Análise
Inspeção de `channels.whatsapp.groups`:
```json
{
  "<REDACTED-WHATSAPP-GROUP>": {
    "requireMention": false,
    "systemPrompt": "Este é o grupo Obra BVV B-04 (read-only). Responda NO_REPLY..."
  },
  "<REDACTED-WHATSAPP-GROUP>": {
    "requireMention": false   // ← BUG: sem systemPrompt safeguard
  }
}
```

Padrão de design da config existente:
- Grupo BVV (`...05821875644`) usa `requireMention: false` mas adiciona systemPrompt instruindo `NO_REPLY` → silencioso
- Grupo `...06761666150` tinha mesma config sem o safeguard → **responde tudo**

Comparação com backup pre-upgrade (`/var/backups/openclaw-pre-5.6-20260507-1353/openclaw.json`): **diff vazio**. Config já estava errada antes do upgrade. Visibility surgiu hoje pelo primeiro tráfego no grupo.

### Fix aplicado
```bash
# Via Python (CLI config set falha em key com '@' e '.')
python3 -c '
import json
data = json.load(open("/root/.openclaw/openclaw.json"))
g = data["channels"]["whatsapp"]["groups"]["<REDACTED-WHATSAPP-GROUP>"]
g["requireMention"] = True
g["systemPrompt"] = "Grupo WhatsApp privado. Só responda quando explicitamente mencionado (@nox)."
json.dump(data, open("/root/.openclaw/openclaw.json.tmp.fix", "w"), indent=2)
import os; os.replace("/root/.openclaw/openclaw.json.tmp.fix", "/root/.openclaw/openclaw.json")
'

openclaw config validate  # OK
systemctl restart openclaw-gateway
```

Backup: `/root/.openclaw/openclaw.json.bak-pre-whatsapp-fix-20260508-084550`.

### Lição
- **`openclaw config set <path> <val>`** falha com keys contendo `@` ou `.` — schema validator rejeita o "@g.us" parcial. Para config edits cirúrgicos em paths assim, **edit JSON direto via Python + atomic move**.
- **Config defaults silenciosamente errados** podem viver na config por meses sem efeito até primeiro tráfego acionar. Auditoria periódica de `requireMention: false` sem `systemPrompt` é mandatória.

## Incidente 8 (P2) — Memory leak nox-mem-api: bump 2 saturou em 14h

### Sintoma
Canary `semantic-canary.sh` voltou a alertar `/api/search unreachable on port 18802 (2x consecutivo)` ~14h após bump 2 (1800M→2400M aplicado ontem 18:34).

### Análise
- Memory current saturou novamente: 2.4G/2.4G (100% MemoryHigh) com uptime 43min do service
- `memory.events.high` cresceu 4554 → 21793 em 1h pós-restart
- Latency degradou 3s+ sequencial, 8-13s concurrent
- `NRestarts=0` (não foi crash recovery), `dmesg` sem OOM events
- **Memory growth pattern revela leak**: pós-restart 08:00:06 → 1.7G às 08:00:30 → 2.4G às 08:46:58 = **+700MB em 90min**

Confirmação: working set não estabiliza. Cresce com uso (caches embedding/chunk acumulando com queries diárias).

### Fix aplicado (2 prongs)

**Prong 1: Bump 3 (final)**
```ini
# /etc/systemd/system/nox-mem-api.service.d/limits.conf
[Service]
MemoryHigh=3000M    # era 2400M
MemoryMax=3500M     # era 2500M
TimeoutStopSec=20
StartLimitInterval=60s
StartLimitBurst=5
```

**Prong 2: Cron preventivo restart 8x/dia (3h interval)**
```cron
27 1,4,7,10,13,16,19,22 * * * /bin/systemctl restart nox-mem-api >> /var/log/nox-mem-restart.log 2>&1
```

Minute :27 escolhido pra evitar coincidir com :00, :05, :10, :15 (outros crons hourly).

### Resultado pós-restart limpo
- Memory current: 1.5G estável
- Latency: 1.0-1.9s consistente
- Canary 3 OKs consecutivos: 08:17, 08:47, 08:51

### Lição
- Bump sozinho **NUNCA resolve memory leak** — só atrasa. Cron preventivo é o pragmático até root cause.
- Working set steady-state pode levar **horas** pra revelar (vimos no 5.6 lesson: bump 1 pareceu OK em 5min, falhou em 1h45min). Para sizing definitivo, **24h+ load real**.
- Para diagnosticar memory leak vs working set legítimo: comparar `memory.current` em 3 snapshots (1min, 1h, 24h pós-restart). Se cresce monotonicamente sem teto, é leak.
- Long-term: heap snapshot Node.js (`node --inspect`) + memlab pra rastrear.

## Incidente 9 (P3, tech debt) — token-refresh-max.sh quebrado 30 dias

### Sintoma
Investigando trigger do restart 08:00:06, descobri que cron `0 */4 * * * token-refresh-max.sh` **falhava silenciosamente desde ~2026-04-08**:
```
[2026-05-08 04:00] ❌ Falha no refresh. Response:
[2026-05-08 04:00] Token expira em -729.1h     # NEGATIVO = expirou 30 dias atrás
[2026-05-08 08:00] ❌ Falha no refresh. Response:
[2026-05-08 08:00] Token expira em -733.1h
```

### Análise
- `/root/.claude-max/credentials.json` tem token `9wirzMeG...`, expirou **2026-04-07**
- `/root/.claude/.credentials.json` tem token DIFERENTE `Ry9UjsX...`, válido até **2027-04-22** — esse é o que Claude CLI subprocess usa
- `ANTHROPIC_MAX_API_KEY` no `.env` aponta pra `Ry9UjsX...` (o token novo)
- Endpoint `claude.ai/api/auth/oauth/token` retorna response vazia (provável que mudou de API)

**Conclusão:** `/root/.claude-max/` é vestigial — token velho do bootstrap original, substituído pelo `/root/.claude/.credentials.json` em algum upgrade anterior. Cron continuou rodando contra path obsoleto. Sistema funcional 30 dias mesmo sem refresh porque token primário foi renovado por outro mecanismo (Claude CLI internal).

### Risco
Script tinha alerta WhatsApp condicional: `if hours_left < 2 then send WhatsApp alert`. Como token está **MUITO** expirado (`-733h`), a condição passa todo run, mas a chamada de webhook falhou silenciosamente também (provavelmente endpoint trial). Sem ação humana, alerta poderia ter disparado a qualquer momento.

### Fix aplicado (cleanup conservador)
1. **Cron disabled** com comentário explicativo:
```cron
# DISABLED 2026-05-08: vestigial, .claude-max/credentials.json expirou 1 mes atras,
# sistema usa .claude/.credentials.json (Ry9UjsX, expira 2027-04-22)
#0 */4 * * * /root/.openclaw/scripts/token-refresh-max.sh
```

2. **Diretório archived**: `mv /root/.claude-max /var/backups/claude-max.archived-20260508-085750` (48K, recoverable)

3. **Script com warning header + exit 0 imediato:**
```bash
#!/bin/bash
# DISABLED 2026-05-08: vestigial. /root/.claude-max/ archived.
# Token primário em /root/.claude/.credentials.json (válido até 2027-04-22)
# Reativar só após investigar OAuth endpoint correto.
echo 'token-refresh-max.sh DISABLED 2026-05-08 — exit 0' >&2
exit 0
# (original code below as comments)
```

### Validação pós-cleanup
- Gateway `/health`: HTTP 200 ✅
- Anthropic `/v1/messages` com token primário: HTTP 200 ✅
- Zero errors no journal pós-archive ✅

### Lição
- **Tech debt de scripts deprecated** silenciosos é tipo "fail-open" — log de erro acumula, ninguém lê, alerta nunca dispara. Auditoria periódica de cron logs > 14 dias velhos é mandatória.
- **Multi-credential paths em projetos legacy** (`.claude/`, `.claude-max/`, `.claude-dev/`) deixam pegadas após refactor. Ao migrar credenciais, **deletar paths antigos** ou pelo menos archivar — não deixar funcionalmente quebrado e operacionalmente vivo.

## Lições estratégicas (3)

1. **Diff config/scripts pré vs pós ANTES de assumir causalidade.** Quando usuário reporta sintoma após mudança, **2/3 dos casos hoje** tinham causa não-relacionada. Investigar primeiro, não trust o relato.

2. **Memory bump sozinho ≠ memory leak fix.** Bump compra tempo proporcional ao headroom adicionado. Se taxa de leak é constante, retorno linear e necessário forever-bumping. Cron preventivo é honesto: "sabemos que vaza, restartamos antes de dor". Heap profile é a real fix.

3. **Tech debt de credentials/scripts deprecated escala silenciosamente.** Sistema funcionou 30 dias com cron quebrado e ninguém percebeu — porque a função real foi substituída por outro mecanismo, mas o legado não foi removido. **Arquitectural cleanup pós-migração não é opcional.**
