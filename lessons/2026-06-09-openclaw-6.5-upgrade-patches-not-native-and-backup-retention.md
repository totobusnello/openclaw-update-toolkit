# 2026-06-09 — Upgrade OpenClaw 6.1 → 6.5: quando os patches NÃO viram nativos + anatomia de um disco que reenche sozinho

## TL;DR

Upgrade planejado `2026.6.5` (primeiro stable do train 6.5, depois de 5 betas). **A lição central é o oposto da do upgrade anterior:** no 6.1, três monkey-patches viraram correções nativas e foram aposentados. No 6.5, é tentador repetir o gesto — mas **dois dos patches (`empty_response` e `tool-only` do harness claude-cli) NÃO entraram nativos**. Confirmado por `grep` do changelog (os PRs que os cobririam = 0 menções) + 0 ocorrências de `empty_response` em 45 turns pós-upgrade. **Não aposente um patch só porque a versão nova "parece" tê-lo absorvido — verifique o changelog pelo número do PR e prove em runtime.**

Três frentes na sessão, todas líquido-positivas e sem breaking:

1. **Disco reenchendo "sozinho":** causa-raiz multiplicativa — um DB que cresceu para ~1.5G × **3 streams de backup que clonam o DB inteiro** × retenção de 7 dias. Fix de uma linha (apertar retenção) + faxina de junk antigo: 50G liberados.
2. **Upgrade 6.1→6.5** com `apply-patches.sh` como `ExecStartPre` idempotente (reaplica os 2 patches a cada restart, sobrevive ao `npm install -g`).
3. **`doctor --fix --yes`** migrou auth profiles para SQLite — com o risco conhecido de remapear modelos `haiku` retired para `sonnet` (caro). Mitigado capturando baseline antes.

---

## Severidade & impacto

- **Downtime gateway:** ~2min total (2 restarts controlados: pós-upgrade e pós-`doctor --fix`).
- **Sem perda de dados:** config, 32 cron jobs (haiku preservado), auth profiles (migrados + backupeados) intactos.
- **Disco:** 34% → 21% (50G liberados), com a rotina de backup corrigida para não reencher.

---

## Achado 1 — Patches NÃO viram nativos só porque a versão é nova

No upgrade anterior (6.1) a lição foi "leia o código novo, os patches viraram nativos, aposente-os". O reflexo natural no 6.5 é repetir. **Errado.** O bug do caminho `result=""` no parser do harness claude-cli (texto do stream descartado quando o evento final de resultado vem vazio) **persiste no 6.5**.

**Como verificar antes de aposentar um patch (checklist):**

1. **`grep` do changelog pelo número do PR/issue** que cobriria o patch. Zero menções = não foi mergeado. (No nosso caso, o PR upstream que propõe o fix nem tinha resposta de maintainer ainda.)
2. **Inspecione o pre-image no bundle novo:** se o bloco de código que o patch substitui ainda está intacto no `dist/` recém-instalado, o patch é necessário.
3. **Prove em runtime:** depois do upgrade + reaplicação, conte as ocorrências do sintoma nos logs (`grep -c empty_response`/`FailoverError` em N turns). Zero = patch segurando.

**O patch vizinho que confunde:** a versão nova pode trazer um fix *adjacente* que parece o seu mas ataca outro caminho. No 6.5, os PRs de "defer stream start até `message_start`" + "reject empty completion handoffs" + "detect unsigned thinking-only stalls" mexem no caminho **Anthropic-stream/extended-thinking**, não no caminho `cliBackends.claude-cli` que o nosso patch corrige. Parecido ≠ o mesmo.

## Achado 2 — `apply-patches.sh` como `ExecStartPre` idempotente é o padrão certo pra patches que sobrevivem a upgrades

Patches dentro de `/usr/lib/node_modules/openclaw/dist/` são apagados a cada `npm install -g openclaw`. O padrão robusto que usamos:

- **Script idempotente** que: localiza o arquivo do bundle por **conteúdo** (`grep -lF "function createCliJsonlStreamingParser"`), não por hash do nome (o hash muda toda versão); detecta se já está patcheado (marker); faz backup; aplica via `node` (string-replace de bloco exato); valida com `node --check`; e **restaura o backup se a validação falhar**.
- **Wired como `ExecStartPre`** do systemd unit do gateway → roda automaticamente em todo `systemctl restart`, sem depender de cron ou intervenção manual.

Resultado no upgrade: depois do `npm install -g openclaw@<nova>`, o restart re-roda o `apply-patches` e os patches voltam, com os hashes novos do bundle. Verificação independente: `grep -lF "<marker>" dist/*.js`.

**Contraste com a automação que aposentamos no 6.1:** lá tínhamos *também* um canary `*/15min` que reaplicava — perigoso quando o patch vira nativo (reaplicar reverte o ganho). O `ExecStartPre` sozinho é mais seguro: só age no restart, e é trivial desligar (comentar uma linha do unit) quando o fix entrar upstream.

## Achado 3 — `doctor --fix --yes` migra auth/cron pra SQLite, mas pode remapear modelos `haiku` retired → `sonnet` (caro)

O train 6.5 migra **auth profiles** e **cron jobs** de JSON para SQLite no preflight do `doctor`. Dois cuidados:

- **Captura baseline antes:** `openclaw cron list` mostra o modelo de cada job. Crons de heartbeat costumam usar um alias `haiku` barato; se o alias não-datado estiver fora da allowlist de modelos, o `doctor --fix` pode remapeá-lo para o `agents.defaults.model` (tipicamente `sonnet`, muito mais caro). Pré-condição: garantir o **alias datado** do haiku no catálogo de modelos antes do `--fix`. Depois, comparar a distribuição de modelos pré/pós para detectar remap.
- **Auth → SQLite faz backup automático:** os JSON originais viram `*.sqlite-import.*.bak`. Reversível. Mas **snapshot manual antes** de qualquer forma (os profiles podem conter referências de credencial).

No nosso caso: 32 jobs preservados, haiku intacto, auth dos 7 agentes migrada limpa.

---

## Achado 4 — Disco que "reenche sozinho": DB grande × N streams de clone-completo × retenção generosa = inchaço multiplicativo

Sintoma: o disco salta de novo poucos dias depois de uma faxina. Causa-raiz não é vazamento — é **estrutural**:

- Um DB de aplicação cresceu para ~1.5G.
- Existiam **3 streams de backup independentes**, cada um clonando o **DB inteiro**: snapshots pré-operação (vários por noite), daily cru, e daily comprimido. Dois deles **sem compressão**.
- Todos com **retenção de 7 dias**.

Quando o DB engorda, os 7 dias × 3 streams incham **ao mesmo tempo** — é o salto multiplicativo. Pior: dois dos streams (daily cru + daily comprimido) eram **redundantes** — o mesmo backup diário, um gzipado outro não.

**Fix:**
1. **Apertar a retenção** dos snapshots de "desfazer a última operação" para 2 dias (ninguém faz rollback de uma operação de 6 dias atrás). Footprint do backup caiu ~50% e parou de crescer (teto fixo).
2. **Deduplicar streams:** manter o comprimido, encurtar/eliminar o cru.
3. **Faxina de junk one-time** que sempre reaparece: backups de cirurgia git (`filter-branch`), forenses de incidentes resolvidos, dirs `pre-upgrade-<versão>` de versões já superadas.

**Padrão reutilizável:** quando o disco reencher, primeiro `du -sh` nos diretórios de backup e procure **o mesmo dado clonado N vezes**. A retenção é quase sempre o knob errado de tão generosa, e streams redundantes são o desperdício escondido.

## Achado 5 — Como provar que os agentes estão de fato no OAuth (e não caindo em API key paga)

Pergunta recorrente após upgrade: "os agentes estão mesmo rodando no OAuth da assinatura, sem cobrança de API?". Verificação objetiva (não assumir):

```bash
# 1. Distribuição de provider nos turns recentes (OAuth vs API key direto)
journalctl -u <gateway-unit> --since "60 min ago" | grep -cE "provider=claude-cli"   # OAuth
journalctl -u <gateway-unit> --since "60 min ago" | grep -cE "provider=anthropic "    # API key direto
journalctl -u <gateway-unit> --since "60 min ago" | grep -ciE "FailoverError|fallback"

# 2. Credencial OAuth: tipo + tier
#    ~/.claude/.credentials.json -> subscriptionType deve ser "max" (ou "pro")

# 3. Teste ao vivo
echo "responda só: OK" | claude -p
```

No nosso caso: 45/45 turns `provider=claude-cli`, 0 `provider=anthropic`, 0 fallback. A API key existe no `.env` apenas como backstop e **nunca é tocada** — o que também explica por que um warning de "profile de API key sem credencial" é puramente cosmético: o runtime não usa esse caminho.

## Achado 6 — Nem todo warning do `doctor` vale "consertar"

Pós-upgrade o `doctor` ficou com warnings que **não têm impacto funcional**, e onde o fix custa mais risco do que vale:

- **Profile de provider "sem credencial"** cujas "credenciais" são na verdade **referências de env** (`${VAR}`) que o checker de profile não resolve — enquanto o runtime resolve via env normalmente. "Consertar" = re-auth interativo gravando uma chave redundante.
- **Conflito de índice de instalação de plugins** (JSON legado vs estado SQLite) — os plugins carregam de `node_modules` + registry e funcionam (0 erros). Reconciliar exigiria cirurgia no state-DB.
- **Transcripts órfãos** que **regeneram com o uso** — é churn de sessão normal, coberto pela manutenção agendada; não é um fix-uma-vez.

**Lição:** distinga "warning que indica risco" de "ruído cosmético de migração". Para os cosméticos, o custo/risco do fix frequentemente excede o benefício — documente como **aceito** em vez de perseguir um `doctor` zerado.

## Runbook do upgrade (ordem que funcionou)

1. **Faxina + snapshot** (libera espaço, captura rollback: config + auth profiles + crontab + cron jobs).
2. **`npm install -g openclaw@<versão>`** (sobrescreve `dist/`, apaga patches — esperado).
3. **`apply-patches.sh`** (reaplica patches no bundle novo; valida markers + `node --check`).
4. **Atualizar plugins externos** para a mesma versão (NÃO são atualizados pelo install do core).
5. **`doctor`** read-only → revisar migrações pendentes (auth/cron → SQLite). Capturar baseline de modelos dos crons.
6. **`systemctl restart`** o gateway (re-roda `apply-patches` via `ExecStartPre`; recarrega plugins).
7. **`doctor --fix --yes`** se quiser fechar as migrações → **restart de novo** (scheduler/registry recarregam).
8. **Smoke:** versão, harness servindo (turns completando sem fallback), canais reconectados, contagem de cron preservada com modelos intactos.

---

## Sinais de que deu certo

- Gateway `active` na versão nova; porta do gateway escutando.
- Harness servindo turns completos (não só "start") — `... live session turn: ... durationMs=... outBytes=...` sem `FailoverError`/`empty_response`.
- Canais reconectados nos logs de boot (cada provider "ready"/"listening"/"connected").
- Contagem de cron jobs preservada **com os mesmos modelos** (sem remap haiku→sonnet).
- Markers dos patches presentes no `dist/` novo via `grep` independente.
