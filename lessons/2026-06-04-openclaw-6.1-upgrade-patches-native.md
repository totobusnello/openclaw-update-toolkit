# 2026-06-04 — Upgrade OpenClaw 5.27 → 6.1: três monkey-patches viram nativos + dois gotchas de migração

## TL;DR

Upgrade planejado de `2026.5.27` → `2026.6.1` (a `5.28` que estava agendada já havia sido superada; `latest` no npm = `6.1`). Salto de changelog sem nenhuma seção "Breaking". O achado central: **os três monkey-patches que mantínhamos dentro do pacote `openclaw` global viraram correções nativas na 6.1** — todos aposentados, sem reaplicar. Dois sustos no caminho, ambos resolvidos **sem `doctor --fix` cego**:

1. **Gateway não subiu no boot** — `models.providers.openai-codex.api` ficou legacy na 6.1 (`openai-codex-responses` → `openai-chatgpt-responses`). Fix cirúrgico manual; `doctor --fix` teria **removido** o provider Codex inteiro ("openai already exists").
2. **`cron list` zerou** — a 6.1 migra o cron store de `jobs.json` (legacy) para SQLite, mas só com `doctor --fix --yes` **e** um restart depois para o scheduler recarregar.

Bônus: confirmamos que o paliativo `keepalive-harness.sh` (workaround do `MissingAgentHarnessError`, issue #85065) ficou **redundante** na 6.1 — o fix entrou nativo upstream. Keepalive desligado em validação com canary de auto-reversão, e publicamos a confirmação de produção na issue P1.

VPS saiu em `2026.6.1`, harness vivo, 39 crons enabled, 0 `MissingAgentHarness`.

---

## Severidade & impacto

- **Downtime gateway:** ~4min (boot loop de 5 restarts até corrigir o `openai-codex.api` legacy; recuperação em 3s após o fix).
- **Crons parados:** ~10min (migração jobs.json→SQLite exigiu `--fix --yes` + restart; 39 jobs voltaram com histórico intacto).
- **Sem perda de dados:** config, cron jobs (`cron_jobs` 49 rows / `cron_run_logs` 6325 rows) e haiku dated alias (8×) preservados.

## Achado 1 — Três monkey-patches do pacote viraram nativos na 6.1

Mantínhamos três patches **dentro** de `/usr/lib/node_modules/openclaw/dist/` (sobrescritos a cada `npm install -g openclaw`, com toda uma automação de reapply). A 6.1 tornou os três obsoletos:

| Patch | Arquivo | Como a 6.1 resolve nativamente |
|---|---|---|
| **#62028 fratricídio** | `restart-stale-pids` | `getSelfAndAncestorPidsSync()` exclui self+ancestors e `verifyGatewayPidByArgvSync` confirma que o PID é um gateway antes de matar. Faz o cleanup *correto* — nosso patch só *desligava* o cleanup (grosseiro). |
| **empty_response (tool-only)** | `cli-runner` + `claude-live-session` | Flag `allowEmptyAssistantReplyAsSilent` + detecção nativa de `tool_use`/`server_tool_use`/`mcp_tool_use`. |

**Lição:** ao subir de versão, **leia o código novo (não só o marcador do patch)** antes de reaplicar. Reaplicar o #62028 na 6.1 seria contraproducente — reintroduziria gateways stale segurando a porta, porque o patch antigo desabilitava o cleanup que a 6.1 agora faz certo.

**Neutralizar a automação de reapply é obrigatório:** tínhamos `apply-patches.sh` como `ExecStartPre` do systemd unit + um canary `*/15` que detectava "patch ausente" e **auto-reaplicava**. Sem neutralizar, a automação reverteria o ganho da 6.1 a cada 15min/restart. Comentamos: a invocação do `apply-patches`, a linha do canary que chamava `check-monkey-patch.sh`, e atualizamos o `PINNED_VERSION`.

## Achado 2 — Boot falha: `openai-codex.api` legacy (e por que NÃO usar `doctor --fix`)

A 6.1 endureceu a validação de schema de `models.providers`. O valor `api: "openai-codex-responses"` saiu da enum permitida → gateway recusa subir no startup:

```
Gateway failed to start: Invalid config at openclaw.json.
models.providers.openai-codex.api: Invalid input
(allowed: openai-completions, openai-responses, openai-chatgpt-responses, ...)
```

O log sugere `doctor --fix`, **mas o fix é destrutivo aqui**: o doctor renomeia `openai-codex` → `openai` e, como já existe um provider `openai` (são distintos — `openai` = api.openai.com key-based; `openai-codex` = chatgpt.com OAuth, gpt-5.4), ele **remove o openai-codex** ("openai already exists"). Perda do provider Codex.

**Fix correto (cirúrgico, sem `--fix`):** trocar só o valor do campo `api` (2 ocorrências) de `openai-codex-responses` → `openai-chatgpt-responses` via string-replace, validar JSON, restart. O Codex segue acessível (a 6.1 expõe via `github-copilot/gpt-5.4`).

**Lição:** `doctor --fix` opera no config inteiro — pode remapear modelos legacy (o haiku dated alias é um risco conhecido) e remover providers "duplicados". Para um único campo legacy, **corrija à mão**. Reserve `--fix` para migrações que você inspecionou.

## Achado 3 — Cron store migra de `jobs.json` para SQLite (e o `cron list` mente até o restart)

Pós-upgrade, `openclaw cron list` retornou **"No cron jobs"** — assustador, mas os 48+ jobs estavam **íntegros** em `~/.openclaw/cron/jobs.json`. A 6.1 move o cron store para SQLite (`state/openclaw.sqlite`, tabela `cron_jobs`), e:

- `doctor --fix --non-interactive` (safe migrations only) **NÃO** migra o cron (toca 48 jobs com `payload.model` — não é classificado como "safe").
- `doctor --fix --yes` **migra** (consome `jobs.json` → `jobs.json.migrated`, popula `cron_jobs` com 49 rows, preserva `cron_run_logs`).
- Após a migração, o `cron list` **ainda** mostra zero até um `systemctl restart` — o scheduler em memória subiu antes da migração e não recarrega sozinho.

**Lição:** "No cron jobs" pós-upgrade ≠ jobs perdidos. Verifique `state/openclaw.sqlite` (tabela `cron_jobs`) antes de entrar em pânico. Sequência: `doctor --fix --yes` → `systemctl restart` → confirmar com `cron list`.

## Achado 4 — keepalive/warmup eram workaround do `MissingAgentHarnessError` (#85065), agora nativo

O `keepalive-harness.sh` (cron `*/10`) existia para manter o harness `claude-cli` "quente" e evitar o `MissingAgentHarnessError` no idle-resume (issue **#85065**). A investigação do source da 6.1 mostrou que o fix entrou **nativo** e cobre os dois throw sites para `claude-cli`:

- `src/agents/harness/selection.ts` → roteia CLI runtime aliases via `isCliRuntimeAliasForProvider(...)` para o harness OpenClaw (`cli_runtime_passthrough_openclaw`) em vez de lançar.
- `src/agents/model-fallback.ts` → guard `if (isCliAgentRuntime(agentRuntime,cfg)) return` antes do `throw` (`isCliAgentRuntime = isCliRuntimeAlias || isCliProvider`; `isCliRuntimeAlias("claude-cli") === true`).

Mito derrubado: **não era `onStartup:false` o problema** — todos os ~40 plugins bundled são lazy por design. A causa era a ausência de fallback no selection path, não o lazy-load.

**Aposentadoria com rede:** keepalive `*/10` desligado, com canary (`keepalive-aposenta-canary.sh`, `*/15`, auto-expira) que **religa o keepalive e alerta** se o `MissingAgentHarness` reaparecer. Base empírica: zero ocorrências desde 28/mai (pico de 99/dia em 24/mai). `warmup` (boot-only) mantido.

## Checklist acionável (upgrade OpenClaw, generalizado)

1. **Snapshot** config + disco antes. Inventariar patches **dentro** do pacote (`find dist -newer package.json` + grep de marcadores) — esses o `npm install` sobrescreve.
2. **Antes de reaplicar qualquer patch**, leia o código novo: a versão pode ter tornado o patch nativo (e reaplicar pode regredir).
3. **Neutralize automação de reapply** (ExecStartPre, canaries) que possa brigar com fixes nativos.
4. **Phase 7**: plugins externos `@openclaw/*` em `/root/.openclaw/npm/` precisam de `npm install ...@<v>` separado (`npm install -g openclaw` não os atualiza).
5. **Boot falhou com schema inválido?** Corrija o campo à mão. Evite `doctor --fix` cego — ele pode remover providers "duplicados" e remapear modelos (haiku→sonnet caro).
6. **`cron list` vazio pós-upgrade?** Cheque `state/openclaw.sqlite` (`cron_jobs`). Migre com `doctor --fix --yes` + `systemctl restart`.
7. **Revise paliativos antigos**: um upgrade pode tornar workarounds redundantes. Aposente com canary de auto-reversão, não de uma vez.
